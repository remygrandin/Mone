# M006 UX Consistency Catalog

This catalog is the audit-first gate for milestone M006. It scores every dashboard
page (stable `UX-###` IDs) and every API endpoint family (stable `API-###` IDs)
against the rubric below, records the three foundational decisions the corrective
slices build on, and gives every flagged entry a concrete target. Every later fix
in slices S02–S08 references an ID in this file, and "catalog cleared" is meant to
be falsifiable: a companion coverage test asserts that no row is left in a non-`OK`
state without a tracked follow-up. Treat the IDs as permanent handles — renumbering
breaks traceability.

## Rubric

Each catalog row is scored against the dimensions below. A dimension is marked
**OK** when it meets the PASS criterion and **FLAG** when it does not (a FLAG row
must carry a concrete `Target`). Dimensions that do not apply to a given entry are
marked `n/a`.

| # | Dimension | PASS criterion |
|---|-----------|----------------|
| 1 | Terminology / naming | User-visible labels, headings, and nav entries use the canonical term from the glossary (no retired variant). |
| 2 | Empty-state | Every list/collection screen renders an explicit empty-state (message + primary action) when the collection is empty — never a bare blank table. |
| 3 | Loading-state | Async data loads are surfaced through the shared loading-state component, not an ad-hoc spinner or silent gap. |
| 4 | Error-state channel | Errors reach the user through the one shared channel that parses ProblemDetails `detail`/`title`; no raw `ex.Message`, no silent `catch{}`. |
| 5 | Action / button placement | Primary and secondary actions sit in the conventional location for that screen type (page-level action top-right, row actions trailing). |
| 6 | Form patterns | Forms use the shared dialog/validation pattern: labelled fields, disabled submit while invalid, consistent cancel/confirm ordering. |
| 7 | API error / response shape | Endpoint emits RFC-9457 ProblemDetails on error (no bare string, no anonymous `{error=}`, no empty body) and a consistent success DTO shape. |
| 8 | Validation messages | Validation failures return `400` ValidationProblem with per-field errors; the dashboard renders them against the offending field. |
| 9 | Resource naming / pluralization / verb pattern | Route is a plural noun resource with REST verb mapping (`GET` list/`GET` item/`POST` create/`PUT`/`PATCH` update/`DELETE`); no verb-in-path RPC style. |
| 10 | HTTP status-code correctness | Endpoint returns the semantically correct status (`200`/`201`/`204`/`400`/`401`/`403`/`404`/`409`) rather than a catch-all `200` or `500`. |
| 11 | Docs annotation | Endpoint declares OpenAPI `Tags`, a `Summary`, and accurate `Produces`/`ProducesProblem` response types. |
| 12 | List pagination / filtering | Collection endpoints expose consistent pagination + filtering parameters and the dashboard list consumes them (no unbounded full-table fetch). |

## Locked Decisions

Exactly three foundational decisions are locked for M006. They are frozen before
any scoring begins so the rubric and every catalog target reference a stable
foundation.

### D1 — API error shape = RFC-9457 ProblemDetails (reaffirms D037)

The single error response shape across all `Mone.Api` endpoints is RFC-9457
ProblemDetails. Register `AddProblemDetails()` and wire `UseExceptionHandler` +
`UseStatusCodePages`; emit errors with `Results.Problem` / `Results.ValidationProblem`.
No custom error envelope, no bare strings, no anonymous `{error=}` objects, no empty
error bodies. This reaffirms existing decision **D037** (it is already recorded in the
decision register and is NOT re-saved here). The dashboard parses the single
`detail`/`title` shape — see D3.

### D2 — Terminology glossary

Canonical user-visible terms for M006. The "Canonical" column is grounded in the
current `MainLayout.razor` nav labels and the page `@page` titles. Retire the
variants listed; new and corrected screens must use only the canonical wording.

| Canonical term | Meaning | Variants to retire |
|----------------|---------|--------------------|
| Host | A monitored machine/endpoint. | Machine, Server, Target, Node (when meaning a host) |
| Host Group | A named collection of hosts that assignments target. | Group (bare, when ambiguous with role groups), Cluster |
| Probe | A plugin-provided capability that produces metrics for a host. | Check definition, Sensor |
| Checker | A scheduled evaluation of a probe against a host that yields a status. | Check (bare), Monitor, Test |
| Assignment | A binding of a checker/probe to a host or host group. | Binding, Attachment, Mapping |
| Override | A per-host value that supersedes a group-level assignment setting. | Exception, Custom value |
| Effective Assignment | The resolved assignment after group inheritance + overrides are applied. | Resolved config, Computed assignment |
| Plugin | A loadable package that contributes probes/executors. | Extension, Add-on, Module |
| Executor Node | A worker process/host that runs checkers. (Nav label: "Nodes".) | Agent, Runner, Worker (in user-visible text) |
| Notification Config | A configured destination/rule for alert delivery. (Nav label: "Notifications".) | Alert config, Notifier, Channel config |

### D3 — Dashboard state-handling convention

One presentation rule for every dashboard screen:

- **Loading** is surfaced through a single shared loading-state component — not
  per-page bespoke spinners or silent gaps.
- **Empty-state** is required on every list/collection screen: when the collection
  is empty the screen renders an explicit message plus the primary create/add action,
  never a bare blank table.
- **Errors** are surfaced through exactly ONE channel that parses ProblemDetails. The
  current `ApiClient` already converges error bodies via `ExtractMessage`
  (`Services/ApiClient.cs:357`, probing `error`/`detail`/`title`/`message`) and throws
  a typed `ApiException`/`ApiForbiddenException` (`Services/ApiException.cs`) from
  `ThrowIfClientErrorAsync` (`Services/ApiClient.cs:340`). The convention: the UI shows
  the parsed ProblemDetails `detail`/`title` through that one channel — never raw
  `ex.Message`, never a silent `catch{}` that swallows the failure. Once D1 lands
  server-side, `ExtractMessage` collapses to reading `detail`/`title` only.
